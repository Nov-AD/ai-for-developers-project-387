«Запись на звонок» — упрощённый сервис бронирования времени по мотивам [Cal.com](https://cal.com). Владелец календаря публикует доступное время для встреч, а гость выбирает свободный слот и записывается на звонок. Это небольшое, но законченное приложение: весь путь от проектирования и API-контракта до запуска в облаке.

Продолжение проекта: интеграция работы агентов в GitHub-проект.

## Границы проекта

Функциональность намеренно ограничена, чтобы сосредоточиться на главном. В проекте **нет**:

- авторизации и регистрации;
- личных кабинетов;
- интеграций с внешними календарями.

## Роли и сценарии

Владелец календаря один и задан заранее.

**Владелец** заводит типы встреч (у каждого — название, описание и длительность) и смотрит список предстоящих встреч всех типов.

**Гость** заходит без регистрации, выбирает тип встречи, открывает календарь на ближайшие 14 дней и записывается на свободный слот. Слот длится столько же, сколько выбранный тип встречи.

## API и контракт

Обязательная часть работы с API:

- TypeSpec-контракт;
- сгенерированная из него OpenAPI-спецификация;
- клиентский SDK для фронтенда, сгенерированный из OpenAPI.

Перед выбором инструментов нужно проверить, что для языка фронтенда существует генератор клиента из OpenAPI. Серверные типы и маршруты генерируются, если выбранный фреймворк это поддерживает; при отсутствии генератора бекенд реализуется по контракту и проверяется тестами.

## Правила бронирования

- Окно записи — 14 календарных дней; оно сдвигается с течением времени.
- Начало окна — сегодня или завтра (выбирается владельцем).
- Часы работы владельца и часовой пояс выбираются и фиксируются в спецификации.
- Длительность слота равна длительности типа встречи.
- Шаг доступных стартов фиксируется в спецификации.
- Пересечение интервалов запрещено, включая частичное наложение встреч разных типов.
- Следующая встреча может начинаться в момент окончания предыдущей.
- Правила соблюдаются и при двух одновременно пришедших запросах.

## Хранение данных

Данные можно хранить в памяти процесса. В этом случае **перезапуск приложения сбрасывает все записи** — это ограничение важно учитывать при использовании сервиса. База данных с сохранением данных тоже допустима; сохранность после перезапуска отдельным условием приёмки не является.

## Стек

Проект — TypeScript-монорепозиторий на pnpm, где TypeSpec-контракт является единственным источником правды.

- **Платформа:** TypeScript, Node.js 24 LTS, pnpm workspaces
- **Окружение:** mise (`mise.toml`, `mise.lock`) — зафиксированные версии инструментов, задачи и фоновые процессы
- **Контракт:** TypeSpec 1.x (`@typespec/http`, `@typespec/openapi3`) → OpenAPI 3.1
- **Клиентский SDK:** `@hey-api/openapi-ts` — SDK, типы, Zod-схемы и готовые TanStack Query-хуки
- **Бекенд:** Fastify 5 + Zod 4 (`fastify-type-provider-zod`), серверные типы из OpenAPI через `openapi-typescript`
- **Фронтенд:** React 19, Vite 8, TanStack Query 5, Tailwind CSS + shadcn/ui
- **Даты и время:** `date-fns` + `date-fns-tz` — хранение в UTC, границы дней считаются в таймзоне владельца
- **Хранение:** `Map` в памяти процесса за интерфейсом репозитория (см. [«Хранение данных»](#хранение-данных))
- **Тесты:** Vitest, `fastify.inject`, React Testing Library; Playwright + Chromium для e2e с настоящим сервером
- **Деплой:** Docker, один инстанс — Render / Fly.io / Railway

### Структура репозитория

```text
packages/contract/   # TypeSpec-контракт и сгенерированный OpenAPI
packages/sdk/        # сгенерированный клиентский SDK
apps/api/            # Fastify-сервер
apps/web/            # React SPA
```

### Генерация

```bash
mise run codegen      # весь конвейер: TypeSpec → OpenAPI → SDK → серверные типы
mise run build        # codegen + сборка всех пакетов
```

Отдельные шаги доступны и через pnpm:

```bash
pnpm contract:build   # TypeSpec → OpenAPI
pnpm sdk:build        # OpenAPI → SDK, типы, Zod-схемы, query-хуки
pnpm api:types        # OpenAPI → серверные типы
```

Цепочка и выбор генераторов проверены: [docs/toolchain-verification.md](docs/toolchain-verification.md). Соответствие сервера контракту проверяется тестом `apps/api/test/contract.test.ts`.

Полная design-first граница календаря, проверяемые HTTP-примеры и порядок функциональных
срезов: [docs/calendar-contract.md](docs/calendar-contract.md). Объявленный контракт
не означает, что все его маршруты уже реализованы; ранние срезы в интеграционной ветке
сохраняют строгие ошибки недостающих операций до завершения всего сценария.

### Проверки

Все герметичные проверки запускаются одной командой — локально, в Git-хуках и в CI:

```bash
mise run check
```

Задача ставит зависимости из lock-файла (`pnpm install --frozen-lockfile`), затем последовательно запускает:

- `mise run lint` — oxlint с `--deny-warnings` и jactionlint для GitHub Actions;
- `mise run fmt:check` — oxfmt в режиме проверки;
- `mise run typecheck` — TypeScript и TypeSpec (компиляция с `--warn-as-error`);
- `mise run knip` — неиспользуемые файлы, экспорты и зависимости;
- `mise run syncpack` — единые версии зависимостей в монорепо;
- `mise run arch` — границы пакетов и циклы импортов (dependency-cruiser);
- `mise run contract:lint` — vacuum для сгенерированного OpenAPI, минимальный score 90;
- `mise run test` — Vitest: тесты API и компонентов React;
- `mise run test:e2e` — Chromium: полный сценарий владельца и гостей с настоящим API.

Браузерный тест `apps/web/e2e/calendar.e2e.ts` создаёт тип встречи через UI владельца.
Два гостя заранее выбирают один слот: первый получает HTTP 201 и подтверждение,
второй — настоящий HTTP 409, сохранённое имя и обновлённую доступность.
После обновления списка владелец видит ровно одну успешную запись.
Подмен `fetch`, перехвата HTTP и прямого заполнения хранилища нет.

`mise run check` (или отдельно `mise run test:e2e`) сам устанавливает Chromium
и его системные зависимости, собирает SDK, API и SPA и запускает Fastify на
`127.0.0.1:18765` с пустым хранилищем. Fastify отдаёт API и SPA с одного origin,
как в Docker; после теста процесс останавливается, в том числе при ошибке.
Порт должен быть свободен: уже запущенный экземпляр не переиспользуется.
`mise run dev`, Docker, Render и секреты для теста не нужны.
Первый запуск требует сети для загрузки браузера; на Linux установка системных
пакетов требует root/sudo (в GitHub Actions доступно).
При падении screenshot и trace сохраняются в `apps/web/test-results/`.

Безопасные автоправки: `mise run fix` (oxfmt и oxlint `--fix`).

Проверки, которым нужна сеть или база сравнения, вынесены в CI:

- `mise run contract:breaking` — oasdiff сравнивает OpenAPI с базовой ветвью и падает на ломающих изменениях (на pull request);
- `mise run secrets` — Betterleaks сканирует Git-историю;
- `mise run audit` — OSV-Scanner проверяет `pnpm-lock.yaml` и lockfiles двух CLI-интеграций по базе уязвимостей.

Workflow `.github/workflows/ci.yml` вызывает ту же `mise run check` через `jdx/mise-action`, дополнительно перегенерирует артефакты и падает, если `git diff` не пуст, проверяет сообщения коммитов (commitlint), секреты, ломающие изменения контракта и уязвимости. На push в любую другую ветку `.github/workflows/push-check.yml` запускает только `mise run check`. `.github/workflows/security.yml` повторяет сканирование уязвимостей и секретов по расписанию.

### Аудит зависимостей с агентом

[`.github/workflows/security.yml`](.github/workflows/security.yml) объединяет
`schedule` (`0 3 * * *`, каждый день, 03:00 UTC) и
`workflow_dispatch`. Аудит разрешён только из основной ветки; расписание GitHub
также использует только её. Тайм-аут аудита — 20 минут, отдельного сканирования
секретов — 15 минут. Общая группа `concurrency: security` не допускает
параллельных аудитов; новый запуск не отменяет уже работающий.

1. `mise run audit` запускает OSV-Scanner по трём lockfiles. Важно:
   используется `pnpm run audit`, а не встроенная команда `pnpm audit`.
   Находки — входные данные агента, а ошибка сканера останавливает процесс.
2. Закреплённый CLI OpenCode V2 использует `openai/gpt-6.1-sol` через платный
   OpenAI API, без fallback на другую модель или провайдера. В
   **Settings → Secrets and variables → Actions** нужен Secret `OPENAI_API_KEY`
   с доступом к модели и настроенной оплатой API; подписка ChatGPT не заменяет
   оплату API. Ключ передаётся только шагу анализа и внутри него — только вызову
   модели, не проверке политики CLI. При отсутствии ключа анализ останавливается
   с понятной ошибкой до запуска CLI. Остальные агенты сохраняют свои модели.
   Prompt и политика — [агент dependency-audit](.opencode/agents/dependency-audit.md).
   Он объясняет риски и предлагает следующий шаг; у него нет инструментов,
   GitHub-токена или разрешения менять зависимости. Эффективную политику
   проверяет CLI перед вызовом модели; процесс ограничен шестью минутами
   и четырьмя шагами модели.
3. Доверенный publisher проверяет JSON агента: каждая находка должна быть
   разобрана ровно один раз, выдуманные ключи отклоняются. Через `gh` он создаёт
   отдельный Issue на пару «зависимость + уязвимость» с анализом агента,
   версиями, SHA и ссылкой на прогон. Авторизация — `GITHUB_TOKEN`,
   права задания — только `contents: read` и `issues: write`; OIDC/App,
   push, PR и дополнительные Secrets для публикации не нужны.
4. Перед созданием publisher просматривает **открытые и закрытые** Issues бота.
   Стабильный маркер зависит от экосистемы, имени зависимости и идентификатора
   уязвимости (предпочтительно CVE), но не от версии, lockfile и формулировок
   модели. Повтор использует найденный Issue (`reused`), даже если он закрыт,
   без нового комментария. Маркер в теле Issue нужно сохранять.
   Удаление Issue/маркера или изменение идентификатора в OSV нарушает эту гарантию.
   Ошибка чтения истории останавливает публикацию, а не разрешает создать дубль.

Результат — Summary прогона и артефакт
`dependency-audit-<run_id>-<attempt>` на 30 дней: `report.md`, исходный `osv.json`,
лог сканера, `prompt.txt`, `agent-output.jsonl`, `agent-stderr.log`,
проверенная политика, `proposal.json`, `publication.json` и метаданные SHA.
Частичный отчёт сохраняется и при ошибке, если раннер успел его сформировать.
Все эти файлы создаются в `$RUNNER_TEMP`, вне checkout; workflow не делает
коммитов и не загружает домашний каталог CLI. Артефакт перед сдачей нужно
проверить на доступность и срок хранения.

#### Ручная проверка после доставки в main

Открыть **Actions → Security → Run workflow**, выбрать `main`. Если реальных
находок нет, включить `training`: сканер всё равно выполняется, а после чистого
скана добавляется синтетическая находка `TRAINING-0001`.
И отчёт, и созданный Issue явно помечены **«Учебная задача»**; это не
уязвимость проекта. При реальных находках учебная не добавляется.

Эквивалентный запуск и проверка включённого workflow через CLI:

```bash
gh api repos/Nov-AD/ai-for-developers-project-387/actions/workflows/security.yml --jq .state
gh workflow run security.yml --ref main -f training=true
gh run list --workflow security.yml --branch main --event workflow_dispatch --limit 5
# Подставить ID нужного прогона из списка:
gh run view <run-id> --log
gh run download <run-id> --name dependency-audit-<run-id>-1
```

Скачивать артефакт следует вне репозитория. После первого успешного прогона
проверить созданный Issue и повторить запуск с тем же `training=true`.
Во втором `publication.json` должен быть `reused` с той же ссылкой.
Фактического запуска по расписанию для демонстрации ждать не нужно.
Если `state` не `active`, владелец включает workflow в Actions перед сдачей.
В публичном неактивном репозитории GitHub может отключить расписание автоматически.

должен подтверждать `reused`. До этого эти критерии не считаются выполненными.

### Агент OpenCode в GitHub

Workflow [`.github/workflows/opencode.yml`](.github/workflows/opencode.yml)
предназначен для обсуждения задач и работы с кодом через GitHub App OpenCode.
Он обрабатывает новые комментарии (`types: [created]`) в Issue и PR
(`issue_comment`) и на строках diff (`pull_request_review_comment`).
Набор `mentions` задан явно и совпадает со стандартным: `/oc` и `/opencode`. Запуск разрешён
только доверенным участникам; боты и fork PR пропускаются.
Модель — `opencode/deepseek-v4.1-flash-free`.
По согласованию с владельцем используется бесплатный режим без собственного
API-ключа и без Secret модели в GitHub Actions.
Бесплатность этой модели ограничена сроком доступности у провайдера;
платёжная карта для учебной проверки не требуется.
Это осознанное отличие от пункта учебного чеклиста о ключе в Secrets;
оно не подтверждает выполнение этого пункта.
Ответы появляются в обсуждении, логи прогонов — в
[Actions → opencode](https://github.com/Nov-AD/ai-for-developers-project-387/actions/workflows/opencode.yml).

**Решение владельца до первого вызова: `share: true`.** Публикация сессий
OpenCode разрешена для демонстрации и разбора работы агента в учебном проекте.
Сессии могут содержать запросы, код, контекст обсуждения и результаты инструментов.
API-ключи, токены и другие секреты не должны попадать в этот контекст.

Задание ограничено `timeout-minutes: 30`. `concurrency` ограничивает параллельные
запуски по номеру Issue или PR; новый комментарий не отменяет текущий прогон.
**Cancel workflow** в Actions останавливает текущий прогон, **Disable workflow**
отключает будущие запуски. Уже отправленный запрос к модели может продолжить
выполнение по правилам провайдера. При переходе на режим с API-ключом его можно
отозвать у провайдера.
Бюджет можно ограничить в кабинете провайдера, если он поддерживает такую настройку.

Ограничение первого запуска: `gh` в оболочке агента не был авторизован, поэтому
Issue прочитан через публичный GitHub REST API. Предварительный шаг workflow
использовал `gh` успешно, а ответ опубликован GitHub App. Это подтверждает чтение
и ответ, но не доказывает, что `gh` самого агента готов создавать задачи.
Диагностика `dangerous-triggers` не снята; успешный прогон сам по себе не означает,
что интеграция полностью принята.

Подготовка скиллов, авторизация, ограничения и порядок проверки реального
запуска описаны в [docs/agents/opencode.md](docs/agents/opencode.md).
Наличие workflow само по себе не подтверждает работающую интеграцию.

### Авторевью pull requests

[`.github/workflows/pr-review.yml`](.github/workflows/pr-review.yml) отдельно
обрабатывает изменения PR. Обычный CLI OpenCode V2 читает diff, обсуждение,
связанные Issues и снимок CI; отдельное задание публикует замечания через
`gh pr comment`. Авторевью не меняет код и не принимает решение о мерже.

Допускаются доверенные люди и `opencode-agent[bot]` с ветками `opencode/*`
только внутри этого репозитория, с целью в default branch. Fork PR пропускаются.
Код PR не исполняется, GitHub App и OIDC этому workflow не нужны. Сохраняется
согласованная бесплатная модель без нового Secret; сессия не публикуется через Share.
Новый запуск отменяет устаревшее ревью того же PR. Для отключения —
`OPENCODE_AUTO_REVIEW=off` или **Actions → PR auto review → Disable workflow**.

Границы доверия, лимиты и обязательная живая проверка обоих каналов обратной связи —
в [docs/agents/opencode.md](docs/agents/opencode.md#авторевью-pr).
Правила релиза и выбранная авторизация release-please —
в [docs/releases.md](docs/releases.md).

Общий бюджет — **5 попыток на PR**, включая ручные команды, авторевью,
отмены и Re-run; история Actions, а не текст комментария, служит счётчиком.
Шестая попытка отклоняется до установки CLI и вызова модели; отдельный reporter пишет `limit_exhausted`
и «Нужен человек». Условия сохранности истории и другие причины остановки —
в [описании бюджета](docs/agents/opencode.md#общий-бюджет-pr-и-результаты-без-модели).
Критерии независимого ревью — в [`REVIEW.md`](REVIEW.md), шаблон описания —
в [`.github/pull_request_template.md`](.github/pull_request_template.md).
Отдельный [`PR head E2E`](.github/workflows/pr-head-e2e.yml) сохраняет точный
SHA, результат и trace успешного браузерного прогона; перед мержем человек
открывает артефакт и сверяет его с текущим head PR.

### Автотриаж новых Issues

Workflow [`.github/workflows/auto-triage.yml`](.github/workflows/auto-triage.yml)
запускается автоматически при **создании Issue** (`issues: opened`), без `/oc`.
Это только первичная классификация: комментарий с пометкой AI, найденные ограничения
по коду и уточняющие вопросы. Состояние — `needs-triage`; категория `bug` или
`enhancement` добавляется, только если она ещё не задана. Неясная категория
остаётся на решение мейнтейнера. Недостающие лейблы создаёт обычный скрипт,
а не модель.

**Фильтры до вызова модели:**

- только открытые, незаблокированные Issues; PR, боты, редактирование, повторное
  открытие и новые комментарии не запускают автотриаж;
- для внешних авторов аккаунт должен быть не моложе 30 дней **на момент создания
  Issue**; `OWNER`, `MEMBER`, `COLLABORATOR` проходят без проверки возраста;
- пропускаются пустые описания и описания длиннее 12 000 символов, обращения с
  `no-ai`, `security`, `invalid`, `duplicate`, уже принятым решением
  (`needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) или конфликтующими
  категориями;
- повторный прогон пропускает Issue, если бот уже оставил комментарий автотриажа.
  Причина пропуска видна в логах Actions; такие обращения разбираются вручную.

**Права разделены по заданиям:**

| Задание | GitHub-права | Что разрешено |
| --- | --- | --- |
| `analyze` | `contents: read`, `issues: read` | Получить обращение, проверить фильтры, прочитать код из default branch и подготовить предложение |
| `publish` | `contents: read`, `issues: write` | Проверить предложение, добавить разрешённые лейблы и один комментарий только в исходный Issue |

Модель запускается отдельным CLI OpenCode V2 с агентом
[`.opencode/agents/auto-triage.md`](.opencode/agents/auto-triage.md):
разрешены только `read`, `glob`, `grep` и загрузка `triage`.
Shell, правки файлов, субагенты, веб-инструменты и доступ за пределы checkout
запрещены. CLI получает отдельный HOME без GitHub-токенов и ключей провайдеров.
Код из обращений и вложений не исполняется, баги не воспроизводятся.
GitHub App и `id-token: write` этому workflow не нужны.
Токен публикации доступен только отдельному заданию без запуска модели.

Перед публикацией повторно проверяются состояние, лейблы, наличие ответа бота
и неизменность обращения. Некорректный JSON, ошибка API или модели останавливают
публикацию. Скрипт не снимает существующие лейблы, не закрывает Issues, не создаёт
спецификации, тикеты, ветки или PR и не переводит задачу в `ready-for-agent`.
Ограничения GitHub-токена технически исключают push и запись PR; ограничения
инструментов модели не являются отдельной ОС-песочницей.

**Лимиты:** 12 шагов модели, 7 минут на CLI, 10 минут на анализ и 3 минуты на
публикацию; размер ответа и число вопросов проверяются скриптом.
С ручными `/oc`-запусками используется общая очередь по номеру Issue, без отмены
текущего прогона. Это ограничения одного запуска, **не дневной финансовый лимит**.
Модель остаётся `opencode/deepseek-v4.1-flash-free`, без нового Secret и без
автоматического перехода на платную модель. CLI `2.3.2` и его зависимости
зафиксированы отдельным lock-файлом в `.github/auto-triage/` и ставятся через
`npm ci`; зависимости приложения по-прежнему управляются pnpm.
Оба lock-файла входят в `mise run audit`.
Сессия автотриажа не публикуется через Share.

Продолжение обсуждения — новым комментарием мейнтейнера с `/oc`; автоматический
ответ не разрешает реализацию. Обязательны [согласования спеки и
тикетов](docs/agents/delivery.md).

Для отключения задай repository Actions variable `OPENCODE_AUTO_TRIAGE=off`
или выбери **Actions → Auto triage → Disable workflow**. Остановить текущий прогон
можно через **Cancel workflow**; уже отправленный запрос к модели может завершиться
на стороне провайдера.

Workflow заработает после попадания в `main` и только для новых Issues.
Локальные проверки фильтров, издателя и ограничений — `pnpm test:automation`
(входят в `mise run check`); настоящий прогон в GitHub нужно проверить отдельно.

## Установка

Понадобятся только [mise](https://mise.jdx.dev/) и Git. Версии Node.js, pnpm, hk, pitchfork, jactionlint, Betterleaks, OSV-Scanner, vacuum и oasdiff зафиксированы в `mise.toml`, а контрольные суммы загрузок — в `mise.lock`.

```bash
git clone https://github.com/Nov-AD/ai-for-developers-project-387.git
cd ai-for-developers-project-387

mise install        # Node.js, pnpm, hk и pitchfork нужных версий
mise run setup      # зависимости из lock-файла + Git-хуки hk
```

`mise install` автоматически выполняет задачу `install` (`pnpm install --frozen-lockfile`). `mise run setup` дополнительно устанавливает хуки `pre-commit` и `pre-push`; задачу можно запускать повторно. Если включена активация mise в шелле, `setup` выполняется при входе в каталог проекта. При первом запуске mise может попросить подтвердить конфигурацию проекта — выполните `mise trust`.

## Использование

```bash
mise run dev            # запустить API и web, дождаться готовности и показать статус
mise daemons status     # состояние фоновых процессов
mise daemons logs api   # логи API; для фронтенда — logs web
mise daemons stop       # остановить оба процесса
```

`mise run dev` поднимает фоновые процессы через [pitchfork](https://pitchfork.jdx.dev/):

- **API** — Fastify на http://127.0.0.1:3000;
- **web** — Vite на http://127.0.0.1:5173. Перед стартом собирается `@calendar/sdk`, а Vite ждёт готовности API.

Процессы продолжают работать после выхода из задачи, поэтому их можно останавливать и запускать повторно. Порт 5173 зафиксирован: если он занят, Vite завершится с ошибкой, а не переедет на другой порт.

Фронтенд использует history-роутинг: `/` — главная страница, `/book` — страница записи,
`/owner` — страница владельца. Docker-образ отдаёт статику и API одним Fastify-сервером;
прямые ссылки `/book` и `/owner` возвращают `index.html`.

## Docker и деплой

```bash
docker build -t calendar:production .
docker run --rm --name calendar -e PORT=8080 -p 8080:8080 calendar:production
curl --fail http://localhost:8080/health
```

Откройте http://localhost:8080. Приложение запускается автоматически: `CMD` стартует
Fastify на `0.0.0.0` и порту из `PORT` (по умолчанию `3000`). При изменении `PORT`
публикуйте соответствующий порт контейнера через `-p`. В образе — только production-
зависимости API, собранный сервер и SPA; процесс работает от пользователя `node`.
`VITE_API_URL=""` задаётся при сборке: браузер обращается к API на том же origin.
`WEB_ROOT=/app/public` включает раздачу статики; `BOOKING_WINDOW_START` принимает
`today` или `tomorrow` (по умолчанию `tomorrow`).

Render собирает этот же Dockerfile из корня репозитория. Параметры повторного
создания сервиса — в [`render.yaml`](render.yaml): бесплатный web service во
Frankfurt, один инстанс. Образ содержит Docker health check `/health`; Render MCP
создаёт сервис с проверкой TCP-порта, а HTTP проверяется после выката.
Бесплатный сервис может засыпать
при простое; первый запрос после пробуждения выполняется дольше.
**После перезапуска, пробуждения с новым процессом или деплоя все типы встреч и
бронирования сбрасываются.** Постоянного хранилища и авторизации нет.

### Render MCP в OpenCode

Безопасный проектный шаблон — [`opencode.json.example`](opencode.json.example)
(OpenCode V2). Если Render ещё не настроен, скопируйте шаблон в `opencode.json`;
если конфигурация уже есть, добавьте в неё только `mcp.servers.render`, сохранив
остальные настройки. Не переопределяйте уже работающую глобальную конфигурацию
Render без необходимости: проектный объект сервера заменяет глобальный целиком.

1. Откройте `/mcps` в OpenCode, выберите `render` и завершите OAuth-вход в браузере.
2. Убедитесь, что `opencode mcp list` показывает `render connected`.
3. Попросите агента показать workspaces и подтвердите нужный workspace.
4. Попросите агента создать Docker web service из этого GitHub-репозитория
   (`main`, Dockerfile `./Dockerfile`, context `.`, plan `free`, region `frankfurt`).
   Не создавайте второй сервис через Blueprint, если он уже создан через MCP.
5. После успешного деплоя проверьте `/health`, создание типа встречи на `/owner`,
   запись гостя на `/book`, появление записи владельцу и отказ повторного
   бронирования того же слота (`409 SLOT_CONFLICT`).

OAuth-сессии хранятся самим OpenCode вне репозитория и не коммитятся. Шаблон
не содержит ключей. Для неинтерактивного входа Render также поддерживает заголовок
`Authorization: Bearer {env:RENDER_API_KEY}` с `oauth: false`; значение передаётся
окружением процесса OpenCode, **не** через Dockerfile, `render.yaml` или Git.
Локальные `.env*` (кроме `.env.example`) и `.opencode/opencode.json(c)` исключены
из Git. Перед публикацией проверяйте историю командой `mise run secrets`.

Повторяемая HTTP-проверка контейнера или публичного сервиса:

```bash
pnpm test:deployment http://localhost:8080
pnpm test:deployment https://calendar-nov-ad.onrender.com
```

Она проверяет SPA и assets, здоровье API, создаёт демонстрационный тип встречи
и запись, проверяет список владельца и повторный запрос с ответом `409`.
Проверка оставляет синтетические данные в памяти; используйте только учебный сервис.
Если доступ в интернет идёт через `HTTPS_PROXY`, для Node.js включите
`NODE_USE_ENV_PROXY=1`.

Публичный выкат проверен 17.11.2026: HTTP smoke и Chromium без HTTP-подмен прошли
создание типа встречи владельцем, запись гостя, отказ второму гостю на тот же слот
(`409 SLOT_CONFLICT`, имя сохранено) и просмотр предстоящей записи владельцем.
Docker проверен с `PORT=18082`, пользователь `node`, health `healthy`; после
рестарта списки типов встреч и записей пустые. `mise run check` — 130 API-тестов
и 36 UI-тестов; аудит зависимостей и сканирование истории секретов — без находок.
Результаты и PR — в [задаче #17](https://github.com/Nov-AD/ai-for-developers-project-386/issues/17).

### Ограничения учебного приложения

- **Авторизации нет:** страница владельца и API доступны каждому. Это не защищённый
  личный кабинет; предупреждения на `/owner` остаются видимыми.
- **Данные публичны:** не используйте реальные персональные данные.
- **Хранение в памяти:** типы встреч и записи исчезают после перезапуска.
- **Один процесс:** несколько экземпляров не поддерживаются.
- **Часовые пояса:** гость видит слоты в своём поясе, владелец — в `Europe/Moscow`
  с явным обозначением пояса.

Подробности контракта и проверок — в [docs/calendar-contract.md](docs/calendar-contract.md).
