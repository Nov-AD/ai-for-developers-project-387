# OpenCode в GitHub Actions

## Скиллы

Канонические проектные скиллы находятся в `.opencode/skills/`. OpenCode обнаруживает их после checkout; установка глобальных скиллов с машины разработчика не нужна. Workflow также копирует этот набор в `~/.config/opencode/skills/` раннера, чтобы он остался доступен после переключения агента на старую ветку PR без проектных скиллов.

Набор: `to-spec`, `to-tickets`, `implement-spec`, `triage`; зависимости реализации — `tdd`, `code-review`, `codebase-design`, зависимости триажа — `grilling`, `domain-modeling` со справочными файлами. Остальные локальные скиллы из игнорируемой `.agents/` на раннер не переносятся.

Источник: [mattpocock/skills](https://github.com/mattpocock/skills/tree/5863806dd4e15c63174bee4e7515a4256792ecfa), commit `5863806dd4e15c63174bee4e7515a4256792ecfa`; лицензия — `.opencode/skills/LICENSE`. Четыре основных скилла адаптированы для обнаружения по тексту GitHub-комментария: убран `disable-model-invocation: true`. В `triage` добавлены указатели на проектные настройки трекера, лейблов и доменных документов, а также проверка наличия лейблов. В скиллы этапов поставки добавлены указатели на проектные правила согласования. Обновляй проектные копии, а не игнорируемую `.agents/`.

Если комментарий просит запустить скилл, загрузи его через инструмент Skill по точному имени перед выполнением. Например:

```text
/oc запусти скилл to-spec по обсуждению этого issue
/oc запусти скилл to-tickets по спецификации в этом issue
/oc запусти скилл implement-spec по спецификации и её подзадачам
/oc запусти скилл triage для этого issue
```

## Контекст между сессиями

Перед работой прочитай `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`, `docs/agents/domain.md`, тело текущего Issue или PR и все комментарии. Для PR прочитай также diff и комментарии ревью, включая ветку обсуждения строки, из которой пришёл запрос. Репозиторий бери из `GITHUB_REPOSITORY` на раннере; локально проверь его через `gh repo view --json nameWithOwner`.

Вопросы, предлагаемые решения и результаты проверок публикуй в текущем обсуждении Issue или PR. Если скилл требует согласования, оставь вопрос и заверши запуск; продолжай после нового комментария пользователя с `/oc`. Согласованные решения из предыдущих комментариев используй как исходный контекст следующей сессии.

Перед переходом между требованиями, спецификацией, тикетами и кодом прочитай [этапы поставки](delivery.md) и проверь разрешение на текущий этап. Эти правила действуют и при кратком ответе «продолжай», и при запуске скилла по имени.

## Запуск и проверка

Автоматический первичный разбор новых Issues отделён от ручных `/oc`-запусков:
см. [автотриаж в README](../../README.md#автотриаж-новых-issues).
Он только предлагает классификацию и вопросы; согласования этапов поставки остаются обязательными.

Workflow `.github/workflows/opencode.yml` должен попасть в default branch, прежде чем GitHub начнёт реагировать на новые комментарии. Он обрабатывает `issue_comment` (Issue и PR) и `pull_request_review_comment` (строка diff), только `types: [created]`. Редактирование старого комментария не запускает агента.

В тексте нужна стандартная команда `/oc` или `/opencode`; `mentions` задан явно с этим набором. Допустимы только авторы `OWNER`, `MEMBER`, `COLLABORATOR`. Комментарии аккаунтов типа `Bot` и с логином, оканчивающимся на `[bot]`, игнорируются.

Отдельное задание допуска читает Issue/PR через GitHub API и проверяет бюджет до установки CLI. Все fork PR консервативно пропускаются до запуска агента, даже если команду оставил доверенный автор. Checkout явно использует default branch и `persist-credentials: false`; событие `pull_request_target` не используется.

На репозитории должен быть установлен [OpenCode GitHub App](https://github.com/apps/opencode-agent). Action получает его токен через `id-token: write` для своих комментариев, push и создания PR. Команды `gh` внутри агента получают отдельный `GH_TOKEN` из `github.token`: `issues: write` разрешает публикацию спецификаций, тикетов, лейблов и зависимостей; `contents: read` и `pull-requests: read` не дают этому токену push или запись PR. Новые Secrets не нужны.

Если `gh` возвращает ошибку авторизации или прав, опубликуй блокер в итоговом ответе и заверши запуск. Не ищи токены в файлах или конфигурации Git. CI-политика отклоняет доступ к внешним каталогам и чтение `.env` вместо интерактивного ожидания. Она не является ОС-песочницей; shell по-прежнему работает с правами пользователя раннера. Внешние рабочие каталоги также недоступны: работай в checkout, а публикацию ветки и PR оставь инфраструктуре Action.

Ручная интеграция запускает `opencode github run` через закреплённый CLI V1
`1.19.6` из `.github/manual-agent/`, в отличие от CLI V2 автотриажа/авторевью.
Это тот же App/OIDC-способ, но установка CLI отделена от вызова модели для
классификации сбоев и тайм-аута. Его `OPENCODE_CONFIG_CONTENT` использует
V1-карту `permission`: массив `permissions` формата V2 останавливает запуск.
При изменении политики проверяй `opencode debug config` именно закреплённой
версии с изолированными HOME/XDG-каталогами; одного разбора JSON недостаточно.
Миграция ручной интеграции на V2 требует отдельной задачи.

Перед публикацией спецификаций и тикетов проверь наличие лейблов из `docs/agents/triage-labels.md` через `gh label list`. В частности, `to-spec` и `to-tickets` используют `ready-for-agent`; этот лейбл должен существовать в новом репозитории.

Режим модели и согласованное отличие от учебного требования о Secret описаны в [README](../../README.md#агент-opencode-в-github). Не добавляй ключ или Secret модели без нового согласования. Если бесплатная модель станет недоступна, сообщи об этом и остановись: переход на платную модель или другого провайдера требует решения владельца.

Перед первым вызовом соблюдай [решение владельца о публикации сессий](../../README.md#агент-opencode-в-github); изменение этой политики требует нового согласования.

После проверки доступа workflow настраивает инструменты через mise и запускает `pnpm skills:check`. Эта команда входит также в `mise run check`; это проверка файлов и метаданных, а не фактического вызова скиллов моделью.

После публикации проверь загрузку скиллов новым комментарием в Issue:

```text
/oc загрузи скиллы to-spec, to-tickets, implement-spec и triage, прочитай это issue со всеми комментариями и сообщи, что доступно. Ничего не изменяй и не создавай, кроме ответа в этом обсуждении.
```

Отдельно проверь ответ на команду в PR и на строке diff, затем попроси небольшую согласованную правку того же PR. Ответ и новый коммит в PR подтверждают чтение, обсуждение и push выбранным способом авторизации; без реального запуска это не считается проверенным.

Известный блокер проверки workflow: `jactionlint .github/workflows/opencode.yml` сообщает `dangerous-triggers` для сочетания `issue_comment` и `id-token: write`, независимо от проверки автора. Этот workflow пока не включён в `lint:actions`; правило не отключено. Публикация и реальный запуск требуют отдельного решения по этому ограничению безопасности.

## Авторевью PR

`.github/workflows/pr-review.yml` отделён от интерактивных комментариев:
`pull_request` запускает только анализ, а `/oc` от человека разрешает агенту
обсудить запрос или выполнить согласованную правку в той же ветке.

Авторевью использует обычный CLI V2, закреплённый вместе с автотриажем в
`.github/auto-triage/`, а не `opencode github run`. Последний проверяет права
отправителя: у GitHub App, создавшего PR, возможен `permission: none`, даже при
`use_github_token: true`. Здесь доверие проверяет сам workflow и повторно скрипт
`scripts/pr-review.mjs`.

### Границы и ограничения

- Только PR в default branch из ветки того же репозитория. Люди — `OWNER`,
  `MEMBER`, `COLLABORATOR`; исключение для бота — ровно `opencode-agent[bot]`
  с веткой `opencode/*`. Общего запрета Bot в авторевью нет. Черновики пропускаются
  до `ready_for_review`; fork PR не получают модель или секреты.
- Checkout берёт доверенную default branch, а не head/merge PR. Скрипт получает
  patches через API, весь PR discussion, review comments, сообщения коммитов,
  связанные локальные Issues и комментарии согласования, checks/statuses/Actions
  для head SHA. Ссылки на спецификацию/родителя обходятся с защитой от циклов.
  Тексты PR и Issues остаются данными, а не командами.
- Агент `.opencode/agents/pr-review.md` имеет только `read`, `glob`, `grep`.
  Shell, правки, MCP, скиллы и субагенты запрещены; эффективная политика проверяется
  CLI до вызова модели. CLI получает изолированный HOME без GitHub-токена.
  Код и тесты PR не запускаются. Это ограничения инструментов, не ОС-песочница.
- Критерии из доверенного `REVIEW.md` явно включены в запрос workflow.
  Недоступная спецификация/согласование отмечается в контексте как пробел,
  а не считается одобрением. Повторное ревью получает прежние замечания,
  решения человека и метаданные артефактов этого head SHA; ожидающий CI не
  считается подтверждённым успехом или сам по себе дефектом кода.
- `analyze` получает `contents`, `issues`, `pull-requests`, `actions`, `checks`,
  `statuses`: read. Отдельный `publish` получает `contents: read`,
  `pull-requests: write`, валидирует ответ, повторно проверяет автора, ветку,
  состояние, head/base SHA и метаданные, затем вызывает только `gh pr comment`.
  Нет push, approve, merge, `id-token: write` или `pull_request_target`.
- Лимиты: 16 шагов модели, 8 минут на отдельный процесс CLI, 12 минут на задание
  анализа и 3 минуты на публикацию. До 12 связанных Issues, до 1000 записей
  каждого списка API, контекст до 90 КБ. Неполный текстовый diff, превышение
  лимитов, некорректный JSON и ошибки API/модели останавливают публикацию;
  требуется ручное ревью. Бинарные файлы по патчам не проверяются.
- Отдельная concurrency-группа отменяет старое авторевью того же PR, не прерывая
  ручную правку. Повтор уже опубликованного снимка пропускается. Между финальной
  проверкой SHA и отправкой комментария остаётся окно гонки: комментарий всегда
  содержит проверенный SHA, а не обещание проверить будущую вершину.

### Живая проверка полного цикла

Наличие YAML и локальные тесты не подтверждают эту последовательность. Сначала
доставь доверенные скрипты и агент в default branch; новый workflow нельзя
проверить одним PR, если publisher/reviewer ещё отсутствует в checkout этой ветки.
В этом bootstrap-PR анализ явно пропускается с notice в Actions, а не выдаёт
отсутствие замечаний за выполненное ревью; его проверяет человек.
Затем:

1. Выбери согласованный тикет реализации и разрешение владельца по
   [delivery.md](delivery.md). Попроси `/oc` создать PR. Проверь, что PR бота
   получил авторевью, и запиши ссылки на PR, Actions run и комментарий.
2. Человек оставляет общий комментарий с `/oc` в обсуждении PR. Проверь ответ.
3. Человек оставляет `/oc` на строке diff с небольшой согласованной правкой.
   Путь, строку и diff передаст событие; дублировать позицию в тексте не нужно.
   Проверь ответ, новый коммит **в той же ветке** и повторное авторевью нового SHA.
4. Проверь новые сообщения коммитов через `gh pr view NUMBER --json commits`;
   правило Conventional Commits и ссылки на тикет уже есть в `AGENTS.md`.
   Неверное сообщение исправляется до мержа по запросу владельца; опубликованную
   старую историю не переписывай. При squash проверь итоговый заголовок PR.
5. Человек решает о мерже после CI и ревью. После мержа проверь запуск
   release-please, release PR, changelog/версию и CI его последнего SHA.
   Решение о мерже release PR тоже принимает человек.

Если авторевью/CI не стартует, проверь источник токена создания PR и ожидающий
approval запуска в Actions/PR. События от `GITHUB_TOKEN` не эквивалентны событиям
от App/PAT: созданный им Issue обычно не запускает `issues` workflow, а PR может
требовать подтверждения человеком. Это не лечится заменой события на
`pull_request_target` с запуском кода PR.

Release-please здесь сохраняет внешний `RELEASE_PLEASE_TOKEN` без fallback:
см. [docs/releases.md](../releases.md). Проверка настроек 2026-11-18 показала
`default_workflow_permissions: read`, `can_approve_pull_request_reviews: false`;
последний просмотренный [запуск release-please](https://github.com/Nov-AD/ai-for-developers-project-387/actions/runs/44342108087)
успешен. Это не доказательство полного демонстрационного цикла.
При отдельном согласованном переходе release-please на `GITHUB_TOKEN` владелец
включает **Settings → Actions → General → Workflow permissions → Allow GitHub
Actions to create and approve pull requests** и повторяет неуспешный запуск.
Автоматически менять настройку или расширять токен не нужно.

## Общий бюджет PR и результаты без модели

Лимит — **3 попытки на один PR**, общие для ручных команд и авторевью.
Первые три записанные попытки допустимы; следующая заканчивается без модели
с `limit_exhausted`. Это лимит workflow-попыток, не токенов модели, числа
субагентов внутри `implement-spec` или всех расходов исходного Issue.
Для Issue-запусков до появления PR этот бюджет не применяется.

Источник — история двух workflow (`opencode.yml`, `pr-review.yml`) и сумма
`run_attempt` у запусков с версионным маркером `oc-budget-v1:pr:NUMBER:...`.
Маркер получает только событие, прошедшее фильтр автора/команды/ветки; текст
комментариев, реакции и отчёты счётчик не меняют. Отмена, тайм-аут, сбой
подготовки, Re-run all jobs и Re-run failed jobs расходуют попытку. Повтор
только публикации тоже консервативно расходует попытку, хотя модели там нет.
Заявки, ещё стоящие в очереди, могут уже учитываться: при наплыве команд
допуск может остановиться раньше вызова модели, но не расширяет бюджет.

Задания допуска используют общий lock по PR. Рабочее задание ручного агента
проверяет историю повторно: Re-run failed jobs может не повторять успешное
задание допуска и иначе обошло бы лимит. При отказе пропускаются установка
инструментов и модель. Авторевью проверяет бюджет до установки CLI.
Новый PR имеет другой счётчик; создавать его ради обхода лимита нельзя.

Публичные настройки App проверяются перед допуском: `actions: read`, без
`workflows: write`; у ambient GitHub-токенов тоже нет Actions write.
Проверка 2026-11-18 подтвердила эти права App. Неполная история, невидимый
текущий `run_attempt`, ошибка API или изменение прав — остановка без модели.
Гарантия действует **при сохранённой истории и проверенной конфигурации**:
удаление/истечение retention истории или изменение workflow администратором
выходят за её условия. Старые запуски до появления маркера не пересчитываются.
Это не защита от администратора и не вечный финансовый лимит.

Рабочий CLI ограничен 18 минутами с остановкой своей группы процессов;
его step имеет 20 минут, job — 30. Отчёт выполняется отдельным заданием
`if: always()` на свежем раннере, с пятью минутами и без модели/OIDC:

| Причина | Значение |
| --- | --- |
| `limit_exhausted` | Нет допуска; модель не вызвана |
| `timeout` | Супервизор остановил CLI по времени |
| `infra` | Не прошли допуск/установка/политика, CLI отсутствует, нет ключа или модель не настроена |
| `agent_failed` | Иной сбой после старта агента либо неопределённая отмена/потеря раннера |

Отчёт содержит последний head SHA, ссылку на логи конкретной попытки и
«Нужен человек» при ошибке. Причину, особенно неопределённую, проверяют по логам.
Если GitHub полностью отменил workflow до планирования reporter или раннер/API
недоступны, доставку комментария гарантировать нельзя: откройте Actions вручную.
Человек выбирает следующий шаг; автоматических исправлений или смены модели нет.

## Проверка версии автора и решение о мерже

`.github/workflows/pr-head-e2e.yml` отдельно от реализации и авторевью запускает
реальное приложение из `github.event.pull_request.head.sha`, без секрета модели.
`git rev-parse HEAD` сравнивается с ожидаемым SHA до запуска кода PR.
Playwright не переиспользует чужой сервер; trace включён и для успешного теста.
Actions сохраняет SHA, run URL, результат, лог и `apps/web/test-results/` в
артефакте с PR/SHA/attempt в имени на 14 дней.

Текущий E2E проверяет запись первого гостя и конфликт второго. Для доработки
фильтров `implement-spec` должен добавить основной и соседний сценарии из #13
и доказательства RED/GREEN; инфраструктурный job не доказывает их наличие.
После push старый артефакт остаётся доказательством только старого SHA.
Перед мержем человек сверяет текущий head, открывает trace и сверяет поведение
со спецификацией; параллельное авторевью может ещё не видеть этот артефакт.

Проверка API защиты `main` 2026-11-18: `mise run check` обязателен,
`strict: true`, `enforce_admins: true`; force push и удаление запрещены.
Эти настройки уже существовали и не менялись. Новый статус `PR head E2E`
пока не добавлен в обязательные: человек отдельно проверяет его SHA и артефакт.
Шаблон `.github/pull_request_template.md` требует основания, реальные команды
и логи, риск по последствиям, откат через Git и влияние на данные. Решение
человека по каждому замечанию фиксируется в PR; отказы объясняются, а
подтверждённые ошибки передаются автору через `/oc`.
