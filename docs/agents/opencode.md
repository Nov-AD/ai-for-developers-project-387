# OpenCode в GitHub Actions

## Скиллы

Канонические проектные скиллы находятся в `.opencode/skills/`. OpenCode обнаруживает их после checkout; установка глобальных скиллов с машины разработчика не нужна. Workflow также копирует этот набор в `~/.config/opencode/skills/` раннера, чтобы он остался доступен после переключения агента на старую ветку PR без проектных скиллов.

Набор: `to-spec`, `to-tickets`, `implement-spec`, `triage`; зависимости реализации — `tdd`, `code-review`, `codebase-design`, зависимости триажа — `grilling`, `domain-modeling` со справочными файлами. Остальные локальные скиллы из игнорируемой `.agents/` на раннер не переносятся.

Источник: [mattpocock/skills](https://github.com/mattpocock/skills/tree/5863806dd4e15c63174bee4e7515a4256792ecfa), commit `5863806dd4e15c63174bee4e7515a4256792ecfa`; лицензия — `.opencode/skills/LICENSE`. Четыре основных скилла адаптированы для обнаружения по тексту GitHub-комментария: убран `disable-model-invocation: true`. В `triage` добавлены указатели на проектные настройки трекера, лейблов и доменных документов, а также проверка наличия лейблов. В скиллы этапов поставки добавлены указатели на проектные правила согласования. Обновляй проектные копии, а не игнорируемую `.agents/`.

Если комментарий просит запустить скилл, загрузи его через инструмент Skill по точному имени перед выполнением. Например:

```text
/oc запусти скилл to-spec по обсуждению этого issue
/oc запусти скилл to-tickets по спецификации в этом issue
/oc запусти скилл implement-spec по спецификации и её подзадачам
/oc запусти скилл triage для этого issue
```

## Контекст между сессиями

Перед работой прочитай `docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`, `docs/agents/domain.md`, тело текущего Issue или PR и все комментарии. Для PR прочитай также diff и комментарии ревью, включая ветку обсуждения строки, из которой пришёл запрос. Репозиторий бери из `GITHUB_REPOSITORY` на раннере; локально проверь его через `gh repo view --json nameWithOwner`.

Вопросы, предлагаемые решения и результаты проверок публикуй в текущем обсуждении Issue или PR. Если скилл требует согласования, оставь вопрос и заверши запуск; продолжай после нового комментария пользователя с `/oc`. Согласованные решения из предыдущих комментариев используй как исходный контекст следующей сессии.

Перед переходом между требованиями, спецификацией, тикетами и кодом прочитай [этапы поставки](delivery.md) и проверь разрешение на текущий этап. Эти правила действуют и при кратком ответе «продолжай», и при запуске скилла по имени.

## Запуск и проверка

Автоматический первичный разбор новых Issues отделён от ручных `/oc`-запусков:
см. [автотриаж в README](../../README.md#автотриаж-новых-issues).
Он только предлагает классификацию и вопросы; согласования этапов поставки остаются обязательными.

Workflow `.github/workflows/opencode.yml` должен попасть в default branch, прежде чем GitHub начнёт реагировать на новые комментарии. Он обрабатывает `issue_comment` (Issue и PR) и `pull_request_review_comment` (строка diff), только `types: [created]`. Редактирование старого комментария не запускает агента.

В тексте нужна стандартная команда `/oc` или `/opencode`; `mentions` задан явно с этим набором. Допустимы только авторы `OWNER`, `MEMBER`, `COLLABORATOR`. Комментарии аккаунтов типа `Bot` и с логином, оканчивающимся на `[bot]`, игнорируются.

Перед checkout workflow проверяет доступ к Issue или PR с комментариями через `gh`. Все fork PR консервативно пропускаются до установки инструментов и запуска агента, даже если команду оставил доверенный автор. Checkout явно использует default branch и `persist-credentials: false`; событие `pull_request_target` не используется.

На репозитории должен быть установлен [OpenCode GitHub App](https://github.com/apps/opencode-agent). Action получает его токен через `id-token: write` для своих комментариев, push и создания PR. Команды `gh` внутри агента получают отдельный `GH_TOKEN` из `github.token`: `issues: write` разрешает публикацию спецификаций, тикетов, лейблов и зависимостей; `contents: read` и `pull-requests: read` не дают этому токену push или запись PR. Новые Secrets не нужны.

Если `gh` возвращает ошибку авторизации или прав, опубликуй блокер в итоговом ответе и заверши запуск. Не ищи токены в файлах или конфигурации Git. CI-политика отклоняет доступ к внешним каталогам и чтение `.env` вместо интерактивного ожидания. Она не является ОС-песочницей; shell по-прежнему работает с правами пользователя раннера. Внешние рабочие каталоги также недоступны: работай в checkout, а публикацию ветки и PR оставь инфраструктуре Action.

Перед публикацией спецификаций и тикетов проверь наличие лейблов из `docs/agents/triage-labels.md` через `gh label list`. В частности, `to-spec` и `to-tickets` используют `ready-for-agent`; этот лейбл должен существовать в новом репозитории.

Режим модели и согласованное отличие от учебного требования о Secret описаны в [README](../../README.md#агент-opencode-в-github). Не добавляй ключ или Secret модели без нового согласования. Если бесплатная модель станет недоступна, сообщи об этом и остановись: переход на платную модель или другого провайдера требует решения владельца.

Перед первым вызовом соблюдай [решение владельца о публикации сессий](../../README.md#агент-opencode-в-github); изменение этой политики требует нового согласования.

После проверки доступа workflow настраивает инструменты через mise и запускает `pnpm skills:check`. Эта команда входит также в `mise run check`; это проверка файлов и метаданных, а не фактического вызова скиллов моделью.

После публикации проверь загрузку скиллов новым комментарием в Issue:

```text
/oc загрузи скиллы to-spec, to-tickets, implement-spec и triage, прочитай это issue со всеми комментариями и сообщи, что доступно. Ничего не изменяй и не создавай, кроме ответа в этом обсуждении.
```

Отдельно проверь ответ на команду в PR и на строке diff, затем попроси небольшую согласованную правку того же PR. Ответ и новый коммит в PR подтверждают чтение, обсуждение и push выбранным способом авторизации; без реального запуска это не считается проверенным.

Известный блокер проверки workflow: `jactionlint .github/workflows/opencode.yml` сообщает `dangerous-triggers` для сочетания `issue_comment` и `id-token: write`, независимо от проверки автора. Этот workflow пока не включён в `lint:actions`; правило не отключено. Публикация и реальный запуск требуют отдельного решения по этому ограничению безопасности.
