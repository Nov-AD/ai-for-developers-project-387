# Design-first граница календаря (#8)

Канонический контракт — [`packages/contract/main.tsp`](../packages/contract/main.tsp).
Правила времени, конкурентности, сортировки, валидации и обработки ошибок входят
в его описания и попадают в OpenAPI. Схемы, SDK, query-хелперы и серверные типы
генерируются; их нельзя исправлять вручную.

## Операции

| Операция SDK | HTTP | Успех |
| --- | --- | --- |
| `getHealth` | `GET /health` | 200, прежний `{ "status": "ok" }` |
| `listMeetingTypes` | `GET /meeting-types` | 200, JSON-массив; исходно `[]` |
| `createMeetingType` | `POST /meeting-types` | 201, сохранённый тип встречи |
| `getAvailability` | `GET /availability?meetingTypeId=<UUID>` | 200, границы окна и слоты |
| `createBooking` | `POST /bookings` | 201, сохранённая запись с типом встречи |
| `listUpcomingBookings` | `GET /bookings` | 200, JSON-массив предстоящих записей |

Точные поля и ограничения см. в TypeSpec, а не в отдельно поддерживаемых интерфейсах.
Например, окончание вычисляет сервер, `Booking.meetingType` содержит полное представление
типа встречи, а `windowEndDate` — исключительная **календарная дата владельца**.
HTTP 400 `INVALID_SLOT` означает недопустимый/устаревший выбор расписания; HTTP 409
`SLOT_CONFLICT` — пересечение записи. Их нельзя объединять в одну ошибку формы.

## Примеры как проверяемые HTTP-подмены

Каждая операция в TypeSpec содержит `x-contract-scenarios`: именованные взаимодействия
с `request.query`/`request.body`, ожидаемыми `status` и `body`. `requestValid: false`
помечает намеренно некорректный запрос. Примеры включают пустые и непустые списки,
пустую доступность, создание, ошибки полей, неизвестные поля/параметры, неизвестный
тип встречи, устаревший выбор и конфликт. Идентификаторы и время примеров демонстрационные.

Для HTTP-подмен фронтенда следует читать эти значения из сгенерированного
`packages/contract/tsp-output/openapi3/openapi.yaml`, а не копировать их в новый
набор ручных DTO. Например, успешный ответ первого среза:

```ts
const scenario = spec.paths['/meeting-types'].get['x-contract-scenarios']
  .find(({ name }) => name === 'empty')
// Подмена HTTP-границы: scenario.status, scenario.body, Content-Type: application/json.
```

`apps/api/test/contract-design.test.ts` проверяет все эти запросы и ответы по
сгенерированным JSON Schema (Ajv 2020-12 с проверкой UUID/date/date-time), включая
соответствие статуса и машинного кода. Проверяются также стандартные OpenAPI-примеры,
созданные `@example`/`@opExample`. Негативные контроли доказывают, что валидатор
отвергает неверный статус, код ошибки и неполный ответ.

Важно для реализации серверной валидации: в OpenAPI 3.1 запрет лишних полей входных
моделей представлен `unevaluatedProperties: { not: {} }`. Генератор Zod 0.99.0
создаёт обычный `z.object`, который сам по себе удаляет лишние поля.
Обработчик обязан использовать строгую валидацию объекта (например, `.strict()`),
а не считать удаление лишних полей выполнением контракта. Контрактные сценарии
с `unknown-field` должны возвращать 400.

## Строгие сценарии сервера

`apps/api/test/contract.test.ts` требует реализации **каждой** операции и запрещает
маршруты вне контракта. HTTP-примеры становятся параметризованными сценариями: данные
подготавливаются только через публичные операции на изолированном экземпляре приложения,
системное время фиксируется средствами Vitest, начало окна — `tomorrow`. Вместо
демонстрационных UUID запросы используют UUID действительно созданных типов встреч.
Пропусков операций, allowlist и фиктивных маршрутов нет: после среза #14 контрактный
гейт зелёный целиком.

## Реализованный сценарий

### Доступность и запись (#12, #13)

Политика владельца зафиксирована в `apps/api/src/config.ts`: `Europe/Moscow`,
понедельник–пятница 09:00–18:00, шаг стартов 30 минут, окно из 14 календарных дат
владельца. `BOOKING_WINDOW_START` принимает `today` или `tomorrow` (по умолчанию
`tomorrow`); любое другое значение останавливает запуск приложения с понятной ошибкой.

`GET /availability` пересчитывается на каждый запрос: окно сдвигается, прошедшие
старты и все записи всех типов исключаются. Пустой список слотов — успешный ответ,
а не ошибка загрузки.

`POST /bookings` заново проверяет тип встречи, окно, день недели, часы, сетку стартов
и будущность начала, сам вычисляет окончание и атомарно проверяет пересечения со всеми
записями всех типов: проверка и вставка выполняются синхронно, без `await` между ними.
Ответы: `400 VALIDATION_ERROR` для полей, `400 INVALID_SLOT` для недопустимого или
устаревшего выбора, `404 MEETING_TYPE_NOT_FOUND`, `409 SLOT_CONFLICT` для пересечения.
Смежные интервалы (конец равен началу следующего) разрешены.

В интерфейсе гостя `POST /bookings` вызывается только по явной отправке формы.
Успех подтверждается данными ответа сервера. При конфликте сохраняются имя и тип,
слот очищается, доступность обновляется. При потере ответа интерфейс не утверждает
ни успех, ни отсутствие записи.

### Предстоящие записи владельца (#14)

`GET /bookings` возвращает записи всех типов, окончание которых строго позже текущего
момента: запись до начала и уже идущий звонок включены, ровно в момент окончания —
исключена. Время пересчитывается на каждый запрос. Сортировка — по началу, затем по UUID.
Необязательные фильтры `guestName`, `meetingTypeId`, `fromDate` и `toDate` сужают выдачу
и комбинируются по AND. `fromDate`/`toDate` — включительные даты `YYYY-MM-DD`, сравниваемые
с календарной датой начала записи в `Europe/Moscow`, а не с UTC или поясом браузера; любая
одна граница допустима. Пустая строка, некорректная дата и `fromDate > toDate` дают
`400 VALIDATION_ERROR`. Невалидный UUID типа даёт `400 VALIDATION_ERROR`, валидный
несуществующий — `200 []`. Пустой список — `200 []`, неизвестный query-параметр —
`400 VALIDATION_ERROR`.

Страница `/owner` показывает предстоящие записи в `Europe/Moscow` с явным обозначением
пояса и перечисляет имя гостя, тип встречи, длительность, начало и окончание. Фильтры
имени гостя, типа встречи и дат «Дата с»/«Дата по» имеют доступные подписи; даты
применяются сразу, а «Сбросить фильтры» очищает все контролы. Загрузка,
пустой список и ошибка чтения отображаются раздельно, у ошибки есть повтор. Список
обновляется при входе на страницу, возврате видимости окна и по кнопке «Обновить
список»; polling, WebSocket и push-уведомления не используются. После успешного
создания записи гость инвалидирует тот же ключ TanStack Query, поэтому отдельного
источника истины о записях нет: владелец всегда читает `GET /bookings`.

## Ограничения

- **Авторизации нет.** Раздел владельца и API открыты каждому, кто обращается к приложению;
  это не защищённый личный кабинет. Предупреждения на странице владельца остаются видимыми.
- **Данные публичны.** Не используйте реальные персональные данные.
- **Хранение только в памяти.** Типы встреч и записи исчезают после перезапуска.
- **Только один процесс.** Несколько экземпляров не разделяют данные и не поддерживаются.
- **Порты.** `mise run dev` поднимает API на `127.0.0.1:3000` и web на `127.0.0.1:5173`;
  `VITE_API_URL` задаёт адрес API для фронтенда. Порт 5173 зафиксирован.
- **Часовые пояса.** Гость видит слоты в своём поясе, владелец — в `Europe/Moscow`.

## Команды проверки

```bash
mise run codegen
pnpm --filter @calendar/api exec vitest run
pnpm --filter @calendar/web exec vitest run
mise run check
```

Повторная генерация не должна оставлять diff в `packages/contract/tsp-output/`,
`packages/sdk/src/` и `apps/api/src/generated/`. `mise run check` — тот же гейт, что
в CI и `pre-push`; ослаблять правила, пропускать тесты или снижать пороги нельзя.

## Свидетельства и блокировки

- Срезы #8–#14 интегрированы в `feat/calendar-spec-7`; каждая операция контракта
  реализована и покрыта строгими сценариями.
- Пересечения проверены тестом
  `rejects overlapping bookings across meeting types` по схеме «зелёный → красный →
  зелёный»: временное разрешение пересечений разных типов давало 201 вместо 409.
- Живой API на свободном порту подтверждал создание типа, слоты, запись, конфликт,
  `INVALID_SLOT` и обновление доступности; полный сквозной прогон записан в отчёте.
- **Браузерный сценарий пройден** на штатных портах после `mise run dev`
  (`http://127.0.0.1:5173`, API `http://localhost:3000`) в реальном Chrome 157 по
  протоколу CDP, без HTTP-моков: пустой список типов, создание типа владельцем,
  выбор типа/дня/слота гостем, подтверждение из ответа сервера, конфликт второго
  гостя (409) с сохранением имени и обновлением доступности, список предстоящих
  записей у владельца, смена типа встречи со сбросом выбора. Записаны шаги,
  фактические запросы и снимки экрана.
- **Release-please (#11)** настроен; секрет `RELEASE_PLEASE_TOKEN` добавлен
  (значение не читалось). Живой выпуск ещё не проверен: release workflow
  запускается только по push в `main`. Это ограничение первого запуска, а не
  замена функциональной приёмки #14.
